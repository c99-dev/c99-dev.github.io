로봇·키오스크·조리사 앱·컨베이어를 연결하는 백엔드

서버를 1인 담당해 하루 200~300잔을 판매하는 매장의 운영을 지원했고, 매장·테스트·전시용 로봇 3대를 다뤘습니다.

  • 주문번호 중복 해결. 키오스크가 여러 대인 매장에서 거의 동시에 들어온 주문에 같은 주문번호가 발급되는 문제가 발생했습니다. 번호 조회와 증가를 한 트랜잭션으로 묶고 SELECT FOR UPDATE와 rollback을 적용한 뒤, 동시 주문 테스트와 실제 운영으로 확인했습니다.
  • 로봇 통신 메시지 깨짐 해결. JAKA 로봇과 서버의 TCP 통신에서 메시지가 서로 붙거나 중간에 잘려 들어오는 문제가 있었습니다. 메시지 경계를 나누는 구분자가 없던 것이 원인이어서, 구분자를 두고 그 단위로 읽도록 바꿔 해결했습니다.
  • 운영 대응. 디카페인 미지원 매장의 주문을 거절하도록 고치고, 서버 원격 재시작과 조리사 앱 복구 절차를 구현했습니다.
  • Flask에서 FastAPI로 전환. 로봇의 대용량 데이터 처리와 API 요청을 함께 처리하기에 Flask 멀티스레드 구조가 맞지 않다고 판단해 FastAPI/ASGI로 옮겼습니다. HTTP 응답·장비 상태·키오스크 서비스와 Socket.IO 중계를 확인하는 회귀 테스트 25건으로 기존 동작을 확인했고, 이후 DB도 PostgreSQL로 전환했습니다.

  • 초기 구조와 재전송. 초기 구조를 설계·개발했습니다. 제어 서버가 전송 지점을 cursor로 저장해, 실패하면 그 지점부터 재전송합니다.
  • 식별·스키마. device_id 식별 체계와 Alembic 마이그레이션을 도입하고, 시간대 통일과 주문 통계 보정에 회귀 테스트를 붙였습니다.

Pionoid

여러 제조사의 로봇을 공통 API로 제어하기 위한 gateway

  • 공통 API와 제조사별 gateway. 메인 Python gateway가 로봇 정보와 명령을 받아 제조사별 Docker SDK gateway로 전달하도록 연동하고, 제조사마다 다른 전원·서보·컨트롤러 처리를 공통 API에 맞췄습니다.
  • 두산 C++ gateway와 AI 활용. C++ SDK가 필요한 두산 gateway는 AI 코드 생성으로 구현하고, 요구사항 정의와 계획 검토, 수정·빌드를 직접 했습니다. SDK 호출 결과뿐 아니라 상태 조회와 실물·시뮬레이터의 상태 변화로 동작을 검증했습니다.

  • 버튼 응답 만료 해결. Discord 버튼은 3초 안에 응답하지 않으면 실패하는데, SQLite 정산이 이벤트 루프를 막아 응답이 늦어지는 문제가 있었습니다. 응답을 먼저 보낸 뒤 저장하도록 순서를 바꾸고 DB 작업을 worker thread로 옮겼습니다.

  • 질의응답 채널을 학습하는 RAG. 관리자 답변이 달린 대화를 매주 Q&A로 수집하고 원문이 수정·삭제되면 근거에서 제외하도록 고도화했습니다. 답변 근거 검증으로 비공개 정보와 폐지된 명령 안내를 막았습니다.
